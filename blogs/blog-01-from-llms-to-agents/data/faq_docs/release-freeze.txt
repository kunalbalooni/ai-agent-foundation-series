Release Freeze Policy

Definition
A release freeze is a scheduled period during which no new code changes, feature deployments, or non-emergency infrastructure modifications are allowed in production environments. The purpose is to reduce risk during high-traffic periods and critical business milestones.

Freeze schedule
- Q4 freeze: 1 December – 2 January (inclusive)
- Holiday freeze: 24 December – 2 January (inclusive, stricter — emergency changes require VP approval)
- Ad-hoc freezes: declared by the Release Manager with at least 48 hours notice via #releases

What is NOT allowed during a freeze
- New feature deployments
- Database schema changes
- Infrastructure changes (scaling policies, network rules, etc.)
- Dependency upgrades unless they are security patches
- Configuration changes that affect user-facing behaviour

What IS allowed during a freeze
- Emergency hotfixes for SEV1 or SEV2 incidents (requires Release Manager approval)
- Security patches for critical CVEs (requires Release Manager + Security Lead approval)
- Read-only configuration updates (e.g. feature flags that disable a feature)

Approval process for emergency changes
1. Engineer opens an emergency-change request in #releases with: description, risk assessment, rollback plan.
2. Release Manager approves or escalates to VP Engineering.
3. Change is deployed with a dedicated change-window and at least two engineers present.
4. Post-deployment confirmation posted in #releases within 30 minutes.

FAQ
- Q: Who declares the freeze?
  A: The Release Manager, with confirmation from the Engineering Director.
- Q: Can I merge PRs during a freeze?
  A: Yes, you can merge to main, but deployments to production are blocked until the freeze lifts.
- Q: What if a SEV1 happens during the freeze?
  A: Follow the SEV1 incident policy. Emergency hotfixes are allowed with Release Manager approval.
- Q: Where do I check the current freeze status?
  A: The #releases Slack channel always has the current freeze status pinned at the top.
